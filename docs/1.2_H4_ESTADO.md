# Estado Actual e Información del Hito: Nearby Connections (B2B-DADM)

Documento consolidado con la arquitectura, archivos involucrados, correcciones críticas aplicadas y el estado funcional actual del módulo de comunicación **Google Nearby Connections**.

---

## 1. Resumen del Hito

El objetivo de este hito fue lograr que dos o más dispositivos Android físicos puedan:
1. Generar y persistir un **Node ID** propio e irrepetible.
2. Solicitar y verificar correctamente todos los permisos necesarios en runtime según la versión de Android (con soporte especial para **Android 13 / API 33+**).
3. Iniciar simultáneamente los roles de **Advertiser** (anunciarse) y **Discoverer** (buscar) mediante la estrategia mesh `P2P_CLUSTER`.
4. Descubrir dispositivos cercanos de forma bidireccional y offline.
5. Permitir la conexión 1-a-1 y el intercambio de mensajes de texto en tiempo real.

**Estado actual:** ✅ **Completamente funcional y verificado en dispositivo físico.**

## 3. Detalle y Responsabilidad de Cada Archivo

### 3.1. Configuración de Plataforma (Android)

#### 📄 `android/app/src/main/AndroidManifest.xml`
- **Responsabilidad:** Declarar todos los permisos requeridos por el sistema operativo y por el stack nativo de Google Play Services.
- **Detalle de permisos:**
  - **Bluetooth Legacy:** `android.permission.BLUETOOTH` y `BLUETOOTH_ADMIN` (sin `maxSdkVersion` para permitir que Google Play Services valide el stack BLE en cualquier versión).
  - **Bluetooth Android 12+ (API 31+):** `BLUETOOTH_ADVERTISE`, `BLUETOOTH_CONNECT`, `BLUETOOTH_SCAN`.
  - **Wi-Fi:** `ACCESS_WIFI_STATE`, `CHANGE_WIFI_STATE` (esenciales para Wi-Fi Direct y Hotspots usados por Nearby; se quitó `maxSdkVersion="31"` para evitar rechazos en Android 13) y `NEARBY_WIFI_DEVICES`.
  - **Ubicación:** `ACCESS_COARSE_LOCATION` y `ACCESS_FINE_LOCATION` (requeridos para escaneo de señales de radio).

#### 📄 `android/app/build.gradle.kts`
- **Responsabilidad:** Configurar las versiones mínimas y de destino del SDK de Android.
- **Puntos clave:**
  - `minSdk = 24`: Exigido por Google Nearby Connections para soportar las capacidades modernas de conectividad peer-to-peer.
  - `targetSdk = flutter.targetSdkVersion` y `compileSdk = flutter.compileSdkVersion`.
  - Java 17 y Kotlin JVM Target 17.

#### 📄 `pubspec.yaml`
- **Responsabilidad:** Declarar dependencias y plugins de Flutter.
- **Paquetes involucrados:**
  - `nearby_connections: ^4.3.0`: API de Google Nearby Connections.
  - `permission_handler: ^11.0.0`: Gestión y diálogo de permisos en runtime.
  - `device_info_plus: ^13.2.0`: Inspección del `sdkInt` del dispositivo para bifurcar lógica de permisos.
  - `shared_preferences: ^2.3.0`: Persistencia local en disco.
  - `uuid: ^4.6.0`: Generación de identificadores únicos.
  - `provider: ^6.1.2`: Inyección de dependencias y reactividad.

### 3.2. Capa de Datos y Servicios

#### 📄 `lib/data/node_id_storage.dart`
- **Responsabilidad:** Obtener o generar de manera persistente el identificador único del nodo.
- **Punto crítico implementado:** El paquete nativo de Nearby y las tramas de BLE tienen límites estrictos de tamaño para el nombre visible (`userName` / advertisement packet). Se genera un ID acortado (`${parts[0]}-${parts[1]}`, ~13 caracteres) para evitar excepciones nativas (`IllegalArgumentException`) en Google Play Services. Si detecta un ID previo mayor a 20 caracteres, lo regenera automáticamente.

#### 📄 `lib/data/chat_message.dart`
- **Responsabilidad:** Modelo de datos para cada mensaje intercambiado.
- **Campos:** `text`, `senderNodeId`, `receiverEndpointId`, `timestamp`, `isMine` (flag booleano que permite diferenciar si el mensaje fue emitido por el usuario local o recibido de un peer para alinearlo en la interfaz).

#### 📄 `lib/data/discovered_endpoint.dart`
- **Responsabilidad:** Modelo inmutable para almacenar la información de un dispositivo remoto detectado (`endpointId` y `userName`).

#### 📄 `lib/data/nearby_service.dart`
- **Responsabilidad:** Fachada que aísla al resto de la aplicación del plugin `nearby_connections`.
- **Puntos clave:**
  - Configura la estrategia `Strategy.P2P_CLUSTER` y el `serviceId = 'com.b2b.dadm'`.
  - Define callbacks para descubrimiento (`onEndpointFound`, `onEndpointLost`), conexiones (`onConnectionInitiated`, `onConnectionResult`, `onDisconnected`) y recepción de datos (`onMessageReceived`).
  - Convierte los mensajes de texto a `Uint8List` (UTF-8) y viceversa mediante `sendBytesPayload`.
  - **Diagnóstico:** Captura cualquier error o `PlatformException` nativa en `lastError` para no perder detalles de depuración.

#### 📄 `lib/services/nearby_permission_handler.dart`
- **Responsabilidad:** Manejar la solicitud de permisos en tiempo de ejecución adaptándose dinámicamente a la versión de Android del teléfono:
  - **Android < 12:** Solicita Ubicación.
  - **Android 12 (API 31):** Agrega `bluetoothScan`, `bluetoothAdvertise`, `bluetoothConnect`.
  - **Android 13+ (API 33):** Agrega `nearbyWifiDevices`.
  - **Verificación de Hardware:** Comprueba activamente si el GPS/Ubicación está encendido en el sistema (`Permission.location.serviceStatus != ServiceStatus.disabled`).

### 3.3. Capa de Estado (Providers)

#### 📄 `lib/providers/node_id_provider.dart`
- **Responsabilidad:** Carga asíncronamente el Node ID al iniciar la app (`loadId()`) y notifica a los widgets cuando está listo.

#### 📄 `lib/providers/nearby_provider.dart`
- **Responsabilidad:** Administrar la máquina de estados de Nearby Connections:
  - Estados: `NearbyState.idle`, `NearbyState.searching`, `NearbyState.connecting`, `NearbyState.connected`, `NearbyState.error`.
  - Orquestar `startSearching()`: valida permisos en runtime, limpia listas previas y arranca en paralelo `startAdvertising` y `startDiscovery`.
  - Si ocurre un fallo nativo, recupera y expone el mensaje detallado de `NearbyService.lastError`.
  - Conexión y auto-aceptación: al iniciar una conexión, la acepta y al confirmarse `Status.CONNECTED` detiene la búsqueda para conservar batería y ancho de banda.
  - Gestión de mensajes entrantes y salientes en la lista observable `messages`.

- **Responsabilidad:** Pantalla interactiva que conmuta según el estado:

  - Presentación clara de mensajes de error con botón para reintentar o abrir la configuración del sistema si faltan permisos.

## 4. Problemas Críticos Identificados y Solucionados

| Problema Encontrado | Causa Raíz | Solución Aplicada |
|---|---|---|
| **Fallo inmediato al iniciar búsqueda en Android 13 (`false` silencioso)** | `maxSdkVersion="31"` en `ACCESS_WIFI_STATE` y `CHANGE_WIFI_STATE` en el Manifest impedía que Android 13 otorgara estos permisos. Google Play Services los requiere internamente para inicializar Nearby. | Se removió `maxSdkVersion="31"` de ambos permisos de Wi-Fi y `maxSdkVersion="28"` de `ACCESS_COARSE_LOCATION`. |
| **Límite de caracteres en BLE** | Se enviaba un UUIDv4 completo (36 caracteres) como nombre visible en `startAdvertising`. BLE tiene un límite estricto de bytes para paquetes de advertising, causando excepciones internas en Play Services. | Se acortó el Node ID a ~13 caracteres (`${uuid1}-${uuid2}`) y se agregó validación de regeneración si existía uno previo de más de 20 caracteres. |
| **Falso positivo en permisos vs. GPS apagado** | El usuario tenía los permisos concedidos en los ajustes, pero el GPS (servicio de ubicación) estaba desactivado en la barra del teléfono. | Se integró la verificación de `Permission.location.serviceStatus` para alertar específicamente sobre el estado del GPS. |
| **Falta de visibilidad ante excepciones nativas** | `NearbyService` capturaba excepciones y retornaba un `false` genérico, dejando la UI con un mensaje ambiguo. | Se implementó la propiedad `lastError` que almacena y propaga el mensaje nativo exacto (`PlatformException`) hacia la UI y los logs. |

## 5. Próximos Pasos Recomendados (Siguiente Hito)

1. **Topología Multi-Peer (Mesh):** Mantener activo el descubrimiento para poder enlazar más de 2 nodos a la vez sin cerrar la búsqueda al conectar el primero.
2. **Protocolo de Paquetes y Enrutamiento:** Implementar una estructura de mensaje serializable en JSON con `origen`, `destino`, `saltos` (TTL) y `payload` para permitir el reenvío de mensajes a través de nodos intermedios (Multi-hop).
3. **Manejo de Desconexiones y Reconexión Automática:** Estrategias de reconexión transparente cuando los dispositivos se alejan y vuelven a entrar en rango de cobertura BLE/Wi-Fi.
