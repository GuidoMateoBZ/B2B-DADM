Documento consolidado con la arquitectura, archivos involucrados, decisiones de diseño, modelo de datos, lógica de ruteo y estado funcional de la implementación del **Punto 6 (Modos de Comunicación)**: Multi-Hop 1-a-1, Broadcast Epidémico (SOS), Persistencia en SQLite y Reforma Integral de la Interfaz de Usuario.

## 1. Resumen del Hito

El objetivo principal de este hito fue transformar la aplicación desde un esquema de chat 1-a-1 directo hacia una **red Mesh Ad-Hoc descentralizada y tolerante a desconexiones**, incorporando persistencia local y soporte para notificaciones del sistema.

### Capacidades Implementadas:
1. **Chat 1-a-1 con Multi-Hop:** Envío de mensajes dirigidos a un nodo específico ruteados automáticamente a través de nodos intermedios cuando el destinatario no se encuentra en rango directo de cobertura BLE/Wi-Fi.
2. **Broadcast Epidémico (SOS):** Emisión de mensajes de emergencia sin destinatario único (`toNodeId = "all"`) propagados por inundación controlada (*flooding*) con deduplicación y tiempo de vida decreciente (*TTL*).
3. **Chat por Node ID (UUID):** Capacidad de iniciar conversaciones ingresando manualmente o pegando desde el portapapeles el identificador único del nodo remoto, sin requerir conexión física previa ni escaneo manual.
4. **Persistencia Local con SQLite:** Almacenamiento privado de mensajes y conversaciones en disco (`sqflite`), permitiendo que el historial y los mensajes sobrevivan al cierre o reinicio de la aplicación.
5. **Notificaciones del Sistema Adaptadas:** Integración con `flutter_local_notifications` incorporando canal prioritario para SOS (`sos_alerts`), discriminación contextual según la pantalla y conversación activa (evita notificar si el usuario ya está leyendo ese chat) y ruteo directo al tocar la notificación.
6. **Reforma Integral de la UI:** 
   - Pantalla principal con lista de conversaciones agrupadas, vista previa del último mensaje, fecha/hora y badge de alcanzabilidad de red.
   - Indicador de estado de la red Mesh: **🟢 Directo**, **🟡 Multi-hop** o **🔴 Sin ruta**.
   - Modal de gestión de vecinos conectados con opción de desconexión manual.
   - Diálogo de nuevo chat con validaciones de Node ID.
   - Pantalla dedicada a Alertas SOS con estilo de emergencia.
   - Acciones de purga: eliminación de mensajes antiguos (> 30 días) y purga total de alertas SOS.
7. **Pruebas Automatizadas:** 16 pruebas unitarias implementadas cubriendo serialización, deduplicación, TTL y reglas de ruteo.

**Estado actual:** ✅ **Completamente implementado, validado con `flutter analyze` (0 advertencias) y verificado con suite de tests al 100%.**

## 3. Detalle y Responsabilidad de Cada Componente

### 3.1. Modelos de Datos (`lib/data/models/`)

#### 📄 `envelope.dart`
- **Rol:** Define el "sobre" o trama de red que viaja por el aire entre dispositivos BLE/Wi-Fi.
- **Estructura:**
  - `messageId` (`String`, UUIDv4): Identificador único global utilizado para deduplicación.
  - `fromNodeId` (`String`): Node ID del emisor original.
  - `toNodeId` (`String`): Node ID del destinatario final, o `'all'` para difusión SOS.
  - `text` (`String`): Contenido del mensaje.
  - `ttl` (`int`): *Time-To-Live* o número de saltos restantes permitidos (valor por defecto: `3`).
  - `timestamp` (`int`): Milisegundos Unix Epoch en que fue originado.
- **Métodos clave:**
  - `Envelope.create(...)`: Factoría que genera `messageId` y marca el `timestamp` actual.
  - `isBroadcast`: Getter que verifica si `toNodeId == Envelope.broadcastAddress ('all')`.
  - `decrementTtl()`: Retorna una copia exacta del sobre con `ttl - 1` para retransmisión.
  - `encode()` / `decode()`: Serialización rápida a JSON UTF-8.

#### 📄 `chat_message.dart`
- **Rol:** Estructura de datos inmutable orientada a la persistencia en base de datos SQLite y al renderizado en la interfaz de usuario.
- **Campos:** `id`, `text`, `senderNodeId`, `receiverId`, `timestamp`, `isMine`.
- **Mapeo bidireccional inteligente (`fromEnvelope`):**
  - Si el sobre es emitido por el dispositivo (`isMine == true`), `receiverId` se fija en `envelope.toNodeId`.
  - Si el sobre es recibido y es broadcast (`envelope.isBroadcast == true`), `receiverId` se fija en `'all'`.
  - Si el sobre es recibido 1-a-1 (`isMine == false`), `receiverId` se fija en `envelope.fromNodeId` (agrupa la conversación bajo el identificador del contacto remoto).
  - Incluye serialización `toMap()` y `fromMap()` compatible con SQLite.

### 3.2. Persistencia en Base de Datos (`lib/data/message_storage.dart`)

- **Tecnología:** SQLite a través de la librería oficial `sqflite` y `path`.
- **Ubicación física en Android:** `/data/data/<package_name>/databases/b2b_messages.db`.
- **Esquema de la tabla `messages`:**
  ```sql
  CREATE TABLE messages (
    id TEXT PRIMARY KEY,
    text TEXT NOT NULL,
    sender_node_id TEXT NOT NULL,
    receiver_id TEXT NOT NULL,
    timestamp INTEGER NOT NULL,
    is_mine INTEGER NOT NULL
  );
  CREATE INDEX idx_receiver_timestamp ON messages(receiver_id, timestamp);
  ```
- **Operaciones implementadas:**
  - `insert(ChatMessage msg)`: Inserción idempotente (`ConflictAlgorithm.ignore`) que evita duplicados si el mismo mensaje llega por múltiples rutas.
  - `getByConversation(String receiverId)`: Recupera el historial cronológico de un chat o del canal SOS (`WHERE receiver_id = ? ORDER BY timestamp ASC`).
  - `getConversations()`: Consulta optimizada con subquery que extrae la lista de contactos recientes junto al último mensaje y su marca temporal para la pantalla principal.
  - `deleteConversation(String receiverId)`: Elimina el historial completo de un contacto.
  - `purgeOlderThan(int days)`: Borrado físico de mensajes con antigüedad superior a $N$ días mediante cálculo epoch.
  - `purgeBroadcasts()`: Borrado exclusivo de todas las alertas SOS (`WHERE receiver_id = 'all'`).

### 3.3. Motor de Enrutamiento y Deduplicación (`lib/services/message_relay.dart`)

- **Rol:** Lógica pura (desacoplada de Flutter y de la UI) que decide la acción a tomar ante cada paquete entrante y saliente.
- **Acciones posibles (`RelayAction`):** `deliver` (entregar a la app), `forward` (retransmitir) y `discard` (ignorar).
- **Mecanismos clave:**
  1. **Deduplicación:** Mantiene una memoria en Set (`_seenMessageIds`). Si un mensaje ya fue procesado o fue emitido por este mismo dispositivo, se descarta de inmediato, impidiendo bucles infinitos en la red mesh.
  2. **Entrega vs. Reenvío 1-a-1:**
     - Si `toNodeId == myNodeId` $\rightarrow$ Entrega local (`deliver`). No se retransmite.
     - Si `toNodeId != myNodeId` y `ttl > 0` $\rightarrow$ Retransmisión (`forward`) con `ttl - 1`. Si el destinatario es un vecino directo, se envía solo a él; si no, se inunda hacia todos los vecinos excepto quien lo transmitió.
  3. **Flooding de Broadcast SOS:**
     - Si `toNodeId == 'all'` $\rightarrow$ Entrega local (`deliver`) y, si `ttl > 0`, reenvío simultáneo a todos los vecinos conectados (excepto el emisor del salto anterior).
  4. **Expiración de TTL:** Todo paquete no dirigido al nodo local cuyo `ttl <= 0` es descartado silenciosamente.

### 3.4. Servicios y Capa de Conectividad

#### 📄 `lib/data/nearby_service.dart`
- Se incorporó el método `sendToEndpoints(List<String> endpointIds, String text)` para transmitir cargas útiles JSON a múltiples vecinos conectados de forma paralela.
- Se refinó `stopAll()` para detener en secuencia conexiones activas, publicidad (*advertising*) y descubrimiento (*discovery*).

#### 📄 `lib/services/local_notification_service.dart`
- **Canales diferenciados:**
  - `chat_messages` (Importancia Alta): Para mensajes regulares 1-a-1.
  - `sos_alerts` (Importancia Máxima): Diseñado con prioridad urgente para alertas de emergencia.
- **Filtrado contextual:** Utiliza `AppNavigationObserver` para inspeccionar la ruta activa y sus argumentos. Si el usuario ya está visualizando el chat con el nodo emisor o la pantalla SOS, la notificación no se dispara, evitando redundancia visual.
- **Navegación por Payload:** Al tocar la notificación nativa, se extrae el payload (`'all'` para SOS o el `nodeId` remitente) y se navega directamente a la conversación respectiva.

### 3.5. Capa de Estado y Reactividad (Providers)

#### 📄 `lib/providers/nearby_provider.dart`
- **Topología Multi-Peer:** Reemplaza la referencia única de conexión por un mapa `_connectedEndpoints` (`endpointId -> nodeId`).
- **Descubrimiento Continuo:** No cancela la búsqueda ni el anuncio al establecer la primera conexión, permitiendo que la red mesh sume nodos dinámicamente.
- **Mitigación de Colisiones en Conexión:** Cuando dos dispositivos se descubren en simultáneo, el nodo con identificador lexicográficamente mayor es el encargado de solicitar la conexión formal, evitando bloqueos cruzados.
- **Evaluación de Alcanzabilidad (`NodeReachability`):**
  - `direct` (🟢): El nodo destino está conectado como enlace inmediato.
  - `multihop` (🟡): No es vecino directo, pero existen otros vecinos conectados que pueden propagar el mensaje.
  - `unreachable` (🔴): Cero vecinos conectados en la vecindad.
- **Integración con MessageRelay:** Procesa los paquetes entrantes en `_onMessageReceived`, entrega los mensajes a `ChatProvider`, dispara notificaciones y despacha los reenvíos multi-hop a través de `NearbyService`.

#### 📄 `lib/providers/chat_provider.dart`
- Administra el historial de mensajes de la conversación activa y la lista general de conversaciones para la pantalla principal.
- Comunica la interfaz con `MessageStorage`, asegurando que cada mensaje enviado o recibido se persista de forma asíncrona y refresque las vistas en memoria.
- Expone los métodos de purga temporal y purga de alertas de emergencia.

## 4. Decisiones de Arquitectura y Diseño Clave

| Aspecto | Decisión Implementada | Justificación Técnica |
|---|---|---|
| **Estructura de Paquetes** | Un solo modelo `Envelope` unificado | Simplifica la serialización JSON y el pipeline de ruteo: si `toNodeId == 'all'` es SOS; si es un UUID, es chat 1-a-1. |
| **Ubicación de Modelos** | Subcarpeta `lib/data/models/` | Adhesión a las convenciones estándar de la comunidad Dart/Flutter (evitando nombres genéricos como `classes/`). |
| **Identificador Remoto** | Campo `receiverId` en base de datos | Clarifica semánticamente que se refiere al UUID del nodo par o a `'all'`, evitando confusiones con IDs abstractos de conversación. |
| **Formato de Marcas Temporales** | `INTEGER` (Epoch en milisegundos) | Permite indexación nativa en SQLite, ordenamiento veloz (`ORDER BY timestamp`), cálculo eficiente de deltas para purgas y conversión directa con `DateTime.fromMillisecondsSinceEpoch()`. |
| **Topología y TTL Inicial** | TTL predeterminado = 3 saltos | Equilibrio óptimo entre alcance de propagación en redes ad-hoc y control de tráfico redundante por inundación. |
| **Ciclo de Vida de Búsqueda** | On-demand con control de usuario | La búsqueda de vecinos no sobrevive al cierre forzado de la app (no requiere Foreground Service con consumo constante de batería en esta fase). |

## 6. Próximos Pasos Recomendados (Hitos Futuros)

1. **Ingreso de Node ID por Código QR:** Incorporar generador y escáner de códigos QR en `NewChatDialog` para intercambiar identidades rápidamente en persona.
2. **Cola de Mensajes Offline (Store & Forward):** Implementar un mecanismo de retención en base de datos para mensajes salientes sin ruta activa, intentando su despacho automático en cuanto un nuevo vecino se conecte a la red mesh.
3. **Servicio en Primer Plano (Foreground Service):** Permitir que Nearby Connections mantenga la conectividad de fondo con una notificación persistente de Android para que la red mesh no se interrumpa si el usuario cambia de app.
4. **Cifrado de Extremo a Extremo (E2EE):** Incorporar intercambio de claves asimétricas (ej. X25519) para que los nodos intermedios que reenvían los paquetes no puedan leer el contenido de los chats 1-a-1.
